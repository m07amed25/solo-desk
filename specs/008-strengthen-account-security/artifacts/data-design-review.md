# Logical field ownership review — T007

Date: 2026-11-03. Evidence: current local source/public documentation; no live target or approval.

Each field is owned by the boundary in its row; app consumption is limited to the stated projection. The original logical table is retained verbatim so no field or trust constraint silently changes:

| Entity / owner                                                               | Minimum logical fields / relationships                                                                                                                                                                                           | Validation and projection                                                                                                                                                                                                                                          |
| ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Account authority / managed identity, consumed by existing server guard      | Stable account ID, original session ID, verified/ban/expiry/revocation status, current authentication context                                                                                                                    | Derived from trusted request/provider state; never asserted through submitted actor/role/session claims. Recheck before effects. Public challenge/recovery has provider-bound limited authority, not an ordinary session substitute                                |
| Capability assessment / server configuration plus accepted evidence          | Operation, selected scope, supported/unavailable/unproven disposition, safe reason code, reviewed policy/evidence version                                                                                                        | Not a provider-plugin detector or new database table. False/unavailable action permission does not mean the account has no factor; unknown provider state stays unknown. Return only safe selection/availability/reason to UI                                      |
| Access method / provider                                                     | Owned opaque reference, kind and authentication role, safe label, pending/active/removed state, optional safe timestamps                                                                                                         | Factor seeds, private keys, credential tokens/challenges and verifier records remain managed. Own-only bounded safe projection; provider payload/IDs that carry bearer authority never reach general client state                                                  |
| Bound intent / existing security boundary, only after support                | Original account/session, supported action/purpose, immutable authoritative targets and digest, method, trusted issue/verification/expiry, pending/cancelled/verified/reserved/consumed state and original operation correlation | Reference alone grants no authority. Existing revocation tables encode revocation-only actions/five-minute proof and cannot be silently broadened. POL-03 supplies each new action's exact proof/challenge rules                                                   |
| Recovery-code set / provider                                                 | Current generation reference, one-use consumption/replacement status, safe remaining-status if supported; one-time presentation and custody acknowledgement as required                                                          | No app code/verifier mirror, no secret read-back, no logs/browser persistence. Code count, format/entropy, lifetime, attempt rules and supported secure storage require provider/security review. Custody acknowledgement does not prove an external backup exists |
| Protection change / provider transaction, safe app outcome only if necessary | Original intent, account-owned intended transition, accepted/rejected/pending/unknown outcome, accepted-state observation and safe correlation                                                                                   | App metadata is conditional on demonstrated cross-request reconciliation need. Never authoritative for factor/identity acceptance if provider state is unknown. Keep external and local commitment distinct                                                        |
| Identity change / provider; unselected optional F02.12                       | Stable account, accepted email/links, separate pending destination/link, provider verification/transaction state and session outcome                                                                                             | No accepted identity update until required verification/commit. Matching email never merges account identity; no business/workspace foreign-key rewrites. Extra identity metadata collection needs inventory approval                                              |
| Minimal security event / existing app boundary                               | Closed event/outcome, known actor where trusted, safe action/opaque reference, correlation/time and policy version                                                                                                               | Use the existing reviewed account-event boundary; extend closed types/constraints only if required. No raw provider JSON, proof, code, email destination or user-controlled log text. Retention/access/hold approval is a collection prerequisite                  |

Decision: no new persistence/table/enum/migration or factor mirror. Account stable ID/original session/status/context come from existing trusted guard/provider. Capability operation/scope/disposition/reason/evidence version are configuration/evidence, not provider state. Access-method references/kind/role/labels/state/times remain provider-owned/unproven for new methods. Intent target/digest/times/states/correlation cannot broaden existing revocation-only proof. Recovery generation/use/replacement/remaining status stays provider-only; custody is not a backup. Accepted identity/pending destination/link and transaction/session state stay provider-owned; optional expansion unselected. Protection transition/outcome/observation/correlation app metadata requires demonstrated reconciliation need and G4 approval. Event actor/action/ref/time/policy are existing minimal event-boundary responsibilities, with new types/retention unapproved.

No SQL history changed; exact wire/schema/index/restore design awaits support and approved policy. External provider commitment and local metadata remain distinct.
