## State transitions and invariants

### Enrollment and sign-in

- Start from a current verified owner with an accepted usable primary method. Explicit setup may enter `pending`; rejected/cancelled/expired setup cannot become active.
- Provider confirmation establishes TOTP possession. Complete enrollment additionally requires supported one-time recovery-material presentation and custody acknowledgement. UI must distinguish provider-accepted factor state from incomplete recovery setup; it must not report the factor disabled merely because setup is incomplete.
- If factor activation and recovery presentation/acknowledgement cannot be safely coordinated by the supported provider, retain the accepted observation and an incomplete/unknown outcome, do not claim rollback. Prove a safe supported resumption/reconciliation path before enabling enrollment.
- Enrolled sign-in enters the provider's pending challenge context and reaches normal protected authority only after the required factor. No ordinary session, stale cookie or alternate entry may bypass this boundary.
- Invalid/replayed/wrong-account/session/purpose/origin proof has no effect. Exact challenge clock/expiry/retry rules await POL-03 and actual provider support.

### Recovery and last routes

- Code verification consumes the selected code once under provider concurrency guarantees and enters only supported limited recovery authority; it cannot itself grant normal profile/business access.
- Revoke every pre-existing session, including an initiating authenticated session. Restore confirmed replacement TOTP and current recovery material, then require fresh compliant sign-in. Once the original session is revoked, neither receipt reads nor resumed dispatch may treat it as authority.
- If any step is unknown, preserve the original change correlation, disclose incomplete recovery and use only provider-supported reconciliation/resumption. Do not consume another code or create a session blindly. No homemade recovery token/session is allowed.
- Usable enrolled configuration means an accepted supported primary method + confirmed TOTP + at least one unused acknowledged current recovery code. A pending/removed/unsupported credential or existing session does not count.
- Last-code recovery must replace recovery material before normal recovery completion. Reject method removals violating the enrolled invariant across concurrent method families. Explicit freshly authorized voluntary MFA disablement is a separate permitted transition only with a usable primary method retained.
- Losing all usable methods/codes has no guaranteed recovery or automatic/support-assisted override in this increment.

### Sensitive/optional changes

- Disablement, replacement and code regeneration require explicit fresh authorization under the approved action matrix; an old session cannot downgrade protection.
- F02.12/F02.13 stay unselected. Their logical transitions remain conditional: verified email/link commit before accepted identity changes; passkey possession/origin/account verification before credential acceptance; owner-only removal after cross-family route checks.
- Removal/expiry never silently transfers stable account, membership/workspace ownership or business records.

## Transactions, concurrency and unknown effects

Provider ownership must supply safe atomic consumption/replacement, enrollment/linkage uniqueness and cross-family last-route enforcement, or the operation remains blocked. App-side locks cannot protect against direct managed endpoints.

If a supported protocol demonstrates a need for application intent/outcome persistence, design the smallest additive extension to the existing boundary after applied-history review. A local transaction must atomically validate current authority/action/targets, claim one operation/digest and record its minimal event before provider dispatch. Equivalent retries reuse the original operation; changed intent conflicts; concurrent dispatch has one claimant. Keep provider I/O outside long database transactions. A lost acknowledgement leaves `unknown`, not a reversible failure; retain reservation and reconcile before another effect.

Any required app metadata gets exact bounded schemas, uniqueness, account/session ownership, targeted lookup/retention indexes and restricted runtime grants during that later design revision. Exact fields/indexes and migration numbers are deliberately not guessed. Existing applied migration checksums remain unchanged. Inventory/retention/hold and real PostgreSQL rollback/commit-unknown/pool isolation acceptance are required before collection. Restore must not resurrect consumed proof, removed factors, revoked sessions or queued effects; provider state must be reconciled before reopening writes.
